#### Modern Certificate Lifecycle
The lifecycle (as described in Ristić's _Bulletproof TLS and PKI_) involves several stages: request, validation, issuance, installation, monitoring, and renewal/revocation.

<span style="color:rgb(219, 0, 0)">Certificate Signing Request (CSR)</span> 
formal request for a CA to sign a certificate, containing the entity's public key and identity info
signed with the corresponding private key (unlike the certificate itself)
the CA may drop some CSR fields and adds its own (e.g., AIA, CRL/OCSP endpoints)

```
You generate a key pair:   private key  +  public key
                                ↓               ↓
You create a CSR:          sign it with     embed it in
                           private key      the CSR
                                    ↓
                          Submit CSR to CA
                                    ↓
                CA validates identity (DCV, etc.)
                                    ↓
             CA builds certificate (adds AIA, OCSP, serial, etc.)
                                    ↓
             CA signs certificate with CA's private key
                                    ↓
                      You receive your certificate
                    
```

#### Top Half — Issuance

**Actors:**

- **Subscriber** — the entity that wants a certificate (e.g., you, running `example.com`)
- **RA (Registration Authority)** — the front-desk of the CA; validates identity but doesn't sign certificates
- **CA (Certificate Authority)** — the entity that actually signs and issues the certificate

**Flow:**

1. The **Subscriber** submits a CSR to the **RA** (the orange circle highlights this as the starting point)
2. The **RA validates the subscriber's identity** — this is where DCV happens (DNS/HTTP challenges, email, etc.)
3. The RA forwards the CSR to the **CA**
4. The **CA issues the certificate** and signs it
5. The certificate flows back to the Subscriber (to be deployed)
6. The CA also **publishes the certificate** to the right — to the CRL Server, OCSP Responder, and CT Logs

#### Bottom Half — Deployment & Verification

**Actors:**

- **Web Server** — the Subscriber's server, now running with the deployed certificate
- **Relying Party** — the client (e.g., your browser) that connects to the web server and needs to verify the certificate

**Flow (numbered steps):**

**① Request certificate** The Relying Party (browser) connects to the Web Server and the server presents its certificate during the TLS handshake.

**② Verify signature** The browser verifies the CA's signature on the certificate — walking the chain of trust up to a trusted root in its trust store.

**③ Check for revocation** The browser checks whether the certificate has been revoked, by contacting either:

- The **CRL Server** — downloads a list of revoked serial numbers
- The **OCSP Responder** — asks in real-time "is this specific certificate still valid?"

The **CT Logs** on the right are checked to ensure the certificate was properly logged (via the embedded SCTs), providing transparency assurance.

**CRL Server** — Certificate Revocation List Server
 
**OCSP Responder** — Online Certificate Status Protocol

An **OCSP Responder** is a server run by (or on behalf of) a CA that answers one simple question in real time:

> _"Is certificate with serial number X currently valid or revoked?"_

Instead of downloading an entire CRL list and searching through it, the client just asks about **one specific certificate** and gets a direct answer.


# Web Certificate Validation

When a TLS client receives a server certificate, it must validate it on seven criteria (revealed incrementally in the slides):

1. Valid chain of trust to a trusted root (each signature verified by the key above it)
2. Domain name matches the CN or SANs (wildcards cover only one level: `*.cs.ru.nl` does not cover `test123.security.this.is.not.working.cs.ru.nl`)
3. Certificate is within its validity period (`NotBefore ≤ now ≤ NotAfter`)
4. Key Usage and Extended Key Usage extensions are compatible with the use
5. Cryptographic keys/algorithms are not too weak (RSA-1024, MD5, and SHA-1 are rejected by browsers)
6. Certificate is included in a Certificate Transparency log
7. Certificate is not revoked

# Domain Control Validation

**Domain-validated (DV) certificates** are issued based on proof of control over a domain name — not proof of organizational identity.

**Traditional methods:** Confirmation email to standard addresses (`admin@`, `administrator@`, `hostmaster@`, `postmaster@`, `webmaster@`, WHOIS contact).

**Modern methods:**
**HTTP/HTTPS file verification:**
	Host a file at `http://domain/.well-known/pki-validation/[unique-file-name].txt`
**DNS verification:**
	Create a CNAME or TXT record to prove DNS zone control
Wildcard certificates (`*.example.com`) typically require DNS-based validation.

#### Attacks Against DCV
Four major attack classes are covered:
##### a) <span style="color:rgb(219, 0, 0)">MD5 Collision Attack</span> (Sotirov et al., 2008)

Using MD5's broken collision resistance, attackers can craft two different certificate bodies that produce the same MD5 hash:

- One for a legitimate domain (CA:False) — this gets legitimately signed by a real CA.
- One for a rogue CA (CA:True) — same hash, so the CA's signature is valid for it too.

Steps: 0. Construct two colliding certificate bodies (different names, CA:False vs CA:True). 1a. Submit the legitimate domain CSR to a real CA and get it signed. 1b. Copy the obtained signature onto the rogue CA certificate — the CA never sees or signs it. 2. Use the rogue CA to issue any certificate (e.g., for `google.com`) with an attacker-controlled key. 3. Present the rogue chain to users — browsers accept it silently.

This attack was demonstrated in 2008 using 200+ PS3 consoles at EPFL (≈2^51.x MD5 compression calls, 30 GB memory). **Fix:** CAs must use SHA-256 or stronger.

```
ATTACKER PREPARES:
┌─────────────────────────────┐    ┌─────────────────────────────┐
│  Certificate A              │    │  Certificate B              │
│  Domain: www.victim.com     │    │  Type: Rogue CA             │
│  CA:False                   │    │  CA:True                    │
│  [S1: hidden in RSA key]    │    │  [S2: hidden in comment]    │
│  [identical suffix]         │    │  [identical suffix]         │
└─────────────────────────────┘    └─────────────────────────────┘
         MD5 hash ──────────────────────── MD5 hash
              ↓                                 ↓
           SAME!  ←──────────────────────→  SAME!

STEP 1: Submit Certificate A's CSR to a real CA
        → CA validates domain ownership (DCV passes)
        → CA signs Certificate A
        → Attacker receives: [Certificate A + CA's signature]

STEP 2: Copy CA's signature onto Certificate B
        → Valid because MD5(A) = MD5(B)
        → Certificate B is now a "CA-signed" rogue CA cert

STEP 3: Use Rogue CA to issue cert for google.com
        → Sign with Rogue CA's private key
        → Browsers trust it (chain: google.com cert → Rogue CA → Real CA → Root)

STEP 4: MITM attack on users visiting google.com
        → Users see no warnings
        → TLS handshake succeeds
        → Connection is decrypted by attacker
```

#### Your Understanding in One Paragraph

> We generated our own CA keypair. We already had the private key — we just needed someone trusted to **sign our public key** so browsers would trust us as a CA. The MD5 collision trick was purely a mechanism to get that signature. Once we have it, we use our private key to sign anything we want, and browsers trust it.

##### b) <span style="color:rgb(219, 0, 0)">DNS Cache Poisoning </span>+ IP Fragmentation Attack
- Exploit IP fragmentation (same IP ID across fragments) to inject a malicious second DNS fragment.
- The first fragment (legitimate) carries correct source port and query ID.
- A forged second fragment overrides the answer section, pointing the domain to the attacker's server.
- The CA then validates the domain challenge against the attacker's server.

The receiver **reassembles** these fragments into the original response. Critically:
- Only **Fragment 1** contains the DNS header (with TXID, source port, query ID)
- **Fragment 2** contains just raw data — no TXID, no port number

```
Step 1: Attacker sends DNS query to resolver for a large record
        (one that will cause fragmentation)

Step 2: Resolver queries the real nameserver
        → Real nameserver sends Fragment 1 (legitimate)
        → Real nameserver sends Fragment 2 (legitimate)

Step 3: Attacker races to send FORGED Fragment 2
        with same IP ID as Fragment 1
        → Contains attacker's fake DNS data

Step 4: Forged Fragment 2 arrives before legitimate Fragment 2
        (or replaces it in reassembly buffer)

Step 5: Resolver reassembles:
        Fragment 1 (legitimate) + Fragment 2 (forged)
        = Poisoned DNS response with valid TXID!
        → No need to guess TXID at all!
```

##### c) <span style="color:rgb(219, 0, 0)">BGP Routing Attacks</span>
- An attacker hijacks BGP routes to redirect the CA's DCV challenge verification request to their own server.
- The CA believes it is communicating with the legitimate domain owner.
- Reference: Sun et al., _Communications of the ACM_, 2024.

#### Certificate Transparency (CT)

**Motivation:** After DigiNotar, there was no record of what had been issued. The goal of CT is to make all certificate issuance public and auditable.

**Core idea:** Shift from single-CA trust (one signature = trusted) to logged trust: certificates must be logged in append-only, tamper-proof public CT logs to be considered valid.

**CT Log Properties:**
- Public, independent, distributed (many operators)
- Append-only and tamper-proof (assuring non-repudiation)
- Audited by monitors

**CT in Practice (Step-by-Step):**
1. Website owner requests a certificate from a CA.
2. CA issues a **precertificate** (same content but no SCT proof yet).
3. CA submits precertificates to CT logs.
4. Logs add the precertificates.
5. Logs return **Signed Certificate Timestamps (SCTs)** — a cryptographic promise to include the cert.
6. CA sends the final certificate (with embedded SCTs) to the domain owner.
7. Browsers verify SCT signatures.
8. Logs are cryptographically monitored for consistency.

**Merkle Trees:** CT logs use Merkle Trees for efficient, tamper-evident structure, allowing O(log n) inclusion proofs. Monitors independently build parts of these trees to detect inconsistencies.

**Auditing:** SCTs must eventually be verified for inclusion (Merkle inclusion proof). The maximum merge delay (MMD) is ~24 hours. Privacy concern: CT logs help attackers discover previously unknown subdomains.

**CT Requirements (Google Chrome):**
- ≤180-day certificates: 2 SCTs from 2 distinct log operators.
- Longer certificates: 3 SCTs.
- At least one Google-operated log must be included.

**Deployment Timeline:**
- Late 2011: Initial idea
- 2013: Google begins planning CT for EV certificates
- 2015: Chrome requires CT for all EV certs
- 2016: Google requires Symantec to log all certificates
- 2017: Chrome 61 adds `Expect-CT` header support
- July 2018: Chrome requires CT for all newly issued certificates
- October 2018: Apple also enforces CT for all certificates

#### <span style="color:rgb(219, 0, 0)">Revocation</span> and Short-Lived Certificates

**When to Revoke:** If a private key is compromised or a certificate was misissued, trust must be withdrawn before the validity period ends.

**Revocation Mechanisms:**
- **CRL (Certificate Revocation List):** Clients download a list of revoked serial numbers from the CA. Simple but can be large and stale.
- **OCSP (Online Certificate Status Protocol):** Client queries a CA server in real-time for the current status of a specific certificate. Issues include: privacy leakage (the CA learns what sites you visit), and **fail-open** behavior (if the OCSP server is unreachable, browsers often proceed anyway).
- **Bottom line: Revocation is hard** — neither CRL nor OCSP is fully reliable in practice.

**ACME (Automated Certificate Management Environment):**
- Protocol for automating the full certificate lifecycle (no manual configuration).
- Clients like `certbot` run scheduled tasks to renew certificates and automatically configure servers.
- Supports HTTP-01 challenge (hosting a file) and DNS-01 challenge (TXT record).
- Largely driven by Let's Encrypt.

**<span style="color:rgb(219, 0, 0)">Shorter</span> Validity as a Solution:**
- The key insight: if certificates expire quickly enough (e.g., 90 days or even shorter), revocation becomes unnecessary in many scenarios — the cert is simply too short-lived to be worth revoking.
- Let's Encrypt pioneered 90-day certificates; there is ongoing movement toward even shorter lifetimes (47-day proposals).
- Short lifetimes force automation (ACME), improving overall hygiene.
